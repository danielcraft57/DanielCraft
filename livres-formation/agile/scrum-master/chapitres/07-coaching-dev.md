# Chapitre 7 - Coaching des Developers

Les **Developers** (au sens large : ceux qui construisent) n'ont pas besoin d'un SM nounou. Ils ont besoin d'un cadre ou ils peuvent s'auto-organiser : planifier ensemble, signaler tot, ameliorer leur facon de livrer, tenir la DoD. Chez DanielCraft, coacher les builders, c'est developper leur autonomie - pas controler leur calendrier.

Lea pose des questions en daily : "qui a besoin d'aide pour le goal ?" Max avait peur de montrer le travail en cours. Sam a normalise les demos moches mid-sprint. Le SM aide aussi sur les pratiques d'equipe : pairage ponctuel, revue de code legere, definition de Done vivante - sans imposer une mode.

Tu proteges contre le micro-management exterieur. Tu encourages la responsabilite collective sur l'increment, pas "chacun sa ticket isolee".

:::retenir
Coaching dev = autonomie, qualite partagee, parole sure - pas surveillance.
:::

## Ce que ce n'est pas

Ce n'est pas assigner les taches une par une. Ce n'est pas devenir tech lead de force. Ce n'est pas non plus laisser pourrir un conflit technique sans facilitation. Ce n'est pas magique : la competence technique reste chez les builders.

## Petite histoire

Deux builders tiraient dans des directions. Lea a facilite quinze minutes : but commun = goal. Ils ont decoupe. Sam a note une regle "deux max en cours". Max a arrete de heroiser seul le jeudi soir. DanielCraft aime ces micro-coachings.

## Erreur classique

Prendre parti technique trop vite. Ou ignorer un frein "humain" (fatigue, silence). Autre piege : daily devenue controle individuel.

:::attention
Si les gens n'osent parler qu'apres la daily dans le couloir, ta facilitation n'a pas encore cree la securite - change le format.
:::

## En vrai

Demande a un builder : "qu'est-ce qui t'empeche d'etre fier de l'increment ce vendredi ?" Ecoute sans corriger dix minutes.

## A toi

Choisis un geste d'autonomie a encourager cette semaine (pairage, demo mid, DoD). Annonce-le. Chez DanielCraft, un geste bat un discours "soyez autonomes".
