# Chapitre 3 - Les roles : PO, SM, Developers

Trois roles, trois jobs distincts. Le **Product Owner** (PO) porte la valeur et les priorites : quoi faire d'abord, pourquoi, pour qui. Le **Scrum Master** (SM) aide l'equipe a bien travailler le cadre : rituels utiles, freins leves, focus protege. Les **Developers** (au sens large : ceux qui construisent) livrent l'increment : design, code, contenu, tests - tout ce qui rend le resultat utilisable. Chez DanielCraft, on explique ca sans costume de ceremonie.

Lea joue souvent PO sur des projets courts : elle coupe le backlog, elle dit non clairement. Max a confondu SM avec "chef de projet qui assigne les taches" - Sam l'a corrige : le SM ne priorise pas le produit, il facilite et debloque. Les Developers ne sont pas des executeurs silencieux : ils co-creent le plan du sprint, estiment, alertent sur le realisable.

Dans une micro-equipe, tu peux cumuler. Cumuler n'efface pas les casquettes : quand tu priorises, tu es PO ; quand tu debloques un frein d'orga, tu es SM ; quand tu construis, tu es Developer. L'honnetete compte plus que le titre sur la carte de visite.

:::retenir
PO = valeur et priorites. SM = cadre et freins. Developers = construire et livrer. Trois casquettes, meme terrain.
:::

## Ce que ce n'est pas

Ce n'est pas "PO = celui qui ecrit des specs de cinquante pages". Ce n'est pas "SM = secretaire de reunion". Ce n'est pas "Developers = junior qui execute sans avis". Ce n'est surtout pas une hierarchie ou le SM commande le PO. Ce n'est pas non plus obligatoire d'avoir trois personnes differentes le jour 1 - mais les responsabilites doivent exister quelque part.

## Petite histoire

Sur une vitrine commerce, Lea (PO) a refuse d'ajouter un blog "parce que c'est tendance". Max (Developer) a propose une page horaires plus claire a la place. Sam (SM) a coupe une daily qui derivait en debate produit. En une semaine, la cliente avait quelque chose d'utile. Sans roles clairs, ils auraient passe le sprint a discuter "qui decide".

## Erreur classique

Transformer le PO en "client absente qui valide a la fin". Ou faire du SM un chef de projet cascade. Ou laisser les Developers hors du planning ("on vous dira quoi faire lundi"). Autre piege : trois titres anglais sur LinkedIn, zero comportement change.

:::attention
Si le PO n'est jamais disponible pendant le sprint, le cadre se vide : l'equipe construit dans le flou.
:::

## En vrai

Pour ton prochain lot, nomme explicitement : qui priorise, qui facilite trente minutes cette semaine, qui construit. Meme si c'est toi trois fois - ecris-le.

## A toi

Remplis : "Mon PO (ou equivalent) est ___ . Mon SM (ou equivalent) est ___ . Mes builders sont ___ ." Si une case dit "personne", c'est ton premier frein a traiter. Chez DanielCraft, on demarre souvent la clarte roles avant les outils.
