# Chapitre 4 - User stories et criteres d'acceptation

Une **user story** raconte un besoin du point de vue de quelqu'un : qui veut quoi, pour quelle raison. Les **criteres d'acceptation** disent comment on saura que c'est bon. Ensemble, ils rendent le backlog discutable et testable. Chez DanielCraft, on prefere des stories courtes et concretes aux romans.

Lea ecrit : "En tant que client presse, je veux voir les horaires sur mobile, pour savoir si j'y vais." Criteres : horaires visibles sans zoom, a jour, page < X secondes ressenties. Max ecrivait "faire la page horaires" sans qui ni pourquoi. Sam ajoute : si on ne peut pas tester un critere, il est flou.

La story n'est pas un contrat juridique. C'est un point de depart de conversation avec les Developers. Le "comment" technique leur appartient souvent.

:::retenir
Story = qui / quoi / pourquoi. Criteres = preuves testables. Conversation > document sacre.
:::

## Ce que ce n'est pas

Ce n'est pas obligatoire d'utiliser la phrase "en tant que" si ca sonne faux - le sens compte. Ce n'est pas une spec complete. Ce n'est pas "le dev n'a pas le droit de poser de questions". Ce n'est pas magique : une story sans ordre dans le backlog reste du bruit.

## Petite histoire

Story panier trop grosse. Lea a decoupe "demande de devis" avec 3 criteres. Max a livre en un sprint. Sam a vu la review simple. DanielCraft recommande la coupe des qu'un item fait peur.

## Erreur classique

Criteres flous ("ergonomique", "rapide"). Stories techniques sans valeur utilisateur. Autre piege : 40 criteres pour une micro-page.

:::attention
Si deux personnes peuvent interpreter un critere de deux facons opposees, il n'est pas encore pret - precise un exemple.
:::

:::astuce
Ajoute un exemple concret sous les criteres ("lundi 9h-12h affiche au-dessus du fold sur telephone").
:::

## En vrai

Reecris un item flou en story + 3 criteres. Fais-le lire a un builder. Ajustez une phrase.

## A toi

Top 3 du backlog en stories propres. Chez DanielCraft, ce top 3 clair change le prochain planning.
